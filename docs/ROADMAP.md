# 開発ロードマップ

## 目的

このドキュメントは、タレントマネジメントシステムをMVPから本番運用可能な新システムへ発展させるための開発ロードマップを整理するものです。

技術方針は `docs/TECH_STACK.md` を前提とし、新システムは `Next.js 16系 App Router + PostgreSQL + Prisma + Auth.js + GitLab CI/CD` を中心に構築します。

## 前提

- MVPは `Next.js + TypeScript + Tailwind CSS + localStorage` で構築済み。
- MVPにはメンバー管理、スキル管理、ロール管理、スキル検索、スキルマップ、統計ダッシュボード、AI評価の基本機能がある。
- 新システムでは `localStorage` を廃止し、`PostgreSQL + Prisma` を主なデータ永続化基盤とする。
- CI/CDはGitLabリポジトリを前提に `GitLab CI/CD` を利用する。
- デプロイは `Docker + Kubernetes` を想定する。
- 初期構成はモジュラーモノリス型Next.jsアプリケーションとする。

## アーキテクチャ方針

新システムは、1リポジトリ、1デプロイ単位から開始します。ただし、内部構造は業務領域ごとに境界を分けるモジュラーモノリス型とします。

想定する主なモジュールは以下です。

- `members`
- `skills`
- `roles`
- `skill-map`
- `dashboard`
- `csv-import`
- `auth`
- `audit`
- `ai-evaluation`

モジュール間はDBテーブルを直接触り合うのではなく、domain service、repository、use caseなどの公開された境界を経由して連携します。これにより、将来的に外部連携、AI評価ジョブ、CSV取り込み処理など一部だけ独立させる必要が出た場合にも分離しやすい構造を保ちます。

## モジュラーモノリス採用の理由

本プロジェクトでは、メンバー、スキル、ロール、評価、監査という業務境界が比較的はっきりしています。一方で、初期段階からマイクロサービス化すると、認証、デプロイ、監視、データ整合性、トランザクション管理の複雑さが先に増えてしまいます。

そのため、まずは1つのNext.jsアプリケーションとして開発速度と運用の単純さを保ちながら、内部のモジュール境界を明確にします。

## モジュラーモノリスへの反論・注意点

- モジュール境界を守らないと、ただの大きなNext.jsアプリになりやすい。
- 初期開発ではディレクトリ設計や依存ルールの分だけ、単純なCRUDアプリより実装コストが少し増える。
- チームが小さい段階では、境界設計を細かくしすぎると開発速度を落とす可能性がある。
- Prisma schemaや共通型が肥大化しやすいため、domain model、DTO、form schemaの分離ルールが必要。
- 将来的なマイクロサービス化を過度に意識しすぎると、現時点で不要な抽象化が増える。

上記を踏まえても、本プロジェクトではモジュラーモノリス型が妥当です。ただし、境界設計は最初から作り込みすぎず、Phase 0または別途 `ARCHITECTURE.md` で最小限のルールとして定義します。

## フェーズ概要

| フェーズ | 名称 | 主な成果物 |
| --- | --- | --- |
| Phase 0 | プロジェクト準備 | 開発方針、ドキュメント方針、ブランチ/MR運用、モジュール境界の初期案 |
| Phase 1 | 要件・ドメイン設計 | データモデル、画面一覧、権限、CSV仕様、主要ユースケース |
| Phase 2 | アプリケーション基盤構築 | Next.js基盤、DB/ORM/Auth基盤、CI/CD、Docker/Kubernetes初期構成 |
| Phase 3 | コア業務機能 | メンバー、スキル、ロール、スキル紐付け、ロール達成判定 |
| Phase 4 | 可視化・検索・ダッシュボード | スキル検索、スキルマップ、統計ダッシュボード、一覧フィルタ |
| Phase 5 | CSV・監査・権限強化 | CSV import/export、監査ログ、RBAC適用 |
| Phase 6 | AI評価機能 | AI評価、キャッシュ、再評価、利用ログ、フォールバック |
| Phase 7 | 本番化・運用準備 | E2E、デプロイ、migration手順、監視、バックアップ、運用ドキュメント |

## Phase 0: プロジェクト準備

### 目的

開発を始める前に、プロジェクト運用、設計ドキュメント、モジュール分割方針を整えます。

### 主なタスク

- `TECH_STACK.md`、`ROADMAP.md`、今後の設計ドキュメント方針を整える。
- GitLabリポジトリ、ブランチ運用、Merge Request運用、Issue管理方針を決める。
- MVPから継承する機能と作り直す機能を整理する。
- モジュラーモノリスのディレクトリ構成と依存ルールを定義する。
- 必要に応じて `ARCHITECTURE.md` を作成し、モジュール境界を具体化する。

### 完了条件

- 開発開始前に参照すべき基本ドキュメントが揃っている。
- モジュール境界と依存方向の初期ルールが説明できる。
- GitLab上の開発運用方針が決まっている。

## Phase 1: 要件・ドメイン設計

### 目的

業務上必要な概念、データ、権限、ユーザーフローを明確にします。

### 主なタスク

- メンバー、部署、スキル、スキルレベル、ロール、評価、監査ログのデータモデルを定義する。
- `members`、`skills`、`roles`、`audit`、`ai-evaluation` などのモジュール境界を定義する。
- 権限ロールの初期案を `admin`、`manager`、`viewer` で定義する。
- 画面一覧と主要ユーザーフローを整理する。
- CSV import/export仕様を固める。
- AI評価を初期リリースに含めるか、後続フェーズにするかを明文化する。

### 完了条件

- 初期リリースに含める業務範囲が明確になっている。
- DB設計と画面設計に進めるだけのドメインモデルがある。
- CSVと権限の基本方針が決まっている。

## Phase 2: アプリケーション基盤構築

### 目的

本番実装を進めるための技術基盤を構築します。

### 主なタスク

- Next.js 16系、TypeScript、Tailwind CSS、shadcn/ui、lucide-reactを導入する。
- PostgreSQL、Prisma、Zod、Auth.jsの基盤を作る。
- モジュール別に domain、application、infrastructure、presentation の配置ルールを整える。
- GitLab CI/CDで `lint`、`typecheck`、`test`、`build`、`SAST` を整備する。
- Docker開発環境を用意する。
- Kubernetesデプロイの初期構成を用意する。

### 完了条件

- アプリケーションがローカルで起動できる。
- DB migrationとPrisma Client生成が実行できる。
- GitLab CI/CDで基本チェックが実行される。
- Dockerコンテナとして起動できる。

## Phase 3: コア業務機能

### 目的

タレントマネジメントの中心となる業務機能を実装します。

### 主なタスク

- メンバー管理のCRUDを実装する。
- スキル管理のCRUDを実装する。
- ロール管理のCRUDを実装する。
- メンバーとスキルの紐付けを実装する。
- スキルレベル管理を実装する。
- ロール達成判定を実装する。
- Repository層をPostgreSQL + Prisma実装として整備する。
- MVPのlocalStorage実装は本番コードへ持ち込まない。
- モジュール間連携は公開されたuse caseまたはservice経由に統一する。

### 完了条件

- メンバー、スキル、ロールを登録、更新、削除、参照できる。
- メンバーにスキルとレベルを紐付けられる。
- ロール要件に基づいて達成状況を判定できる。
- 主要な業務ロジックにユニットテストがある。

## Phase 4: 可視化・検索・ダッシュボード

### 目的

MVPで有効だった可視化・検索機能を、DB集計ベースで再構築します。

### 主なタスク

- メンバー検索を実装する。
- スキル検索を実装する。
- 部署フィルタを実装する。
- ロール保有状況を表示する。
- スキルマップを実装する。
- 統計ダッシュボードを実装する。
- TanStack Tableを一覧・マトリクス表示に導入する。
- 必要箇所のみTanStack Queryを導入する。
- 主要表示をレスポンシブ対応する。

### 完了条件

- スキルや部署から対象メンバーを検索できる。
- スキルマップで全体傾向を確認できる。
- ダッシュボードでメンバー数、スキル数、未設定、ロール保有状況などを確認できる。
- 業務利用に耐える一覧・詳細導線がある。

## Phase 5: CSV・監査・権限強化

### 目的

実運用で必要になる一括処理、操作履歴、権限制御を整備します。

### 主なタスク

- CSV exportを実装する。
- CSV importを実装する。
- import時はプレビュー、検証エラー表示、差分確認、トランザクション登録を行う。
- 監査ログを導入し、作成、更新、削除、import操作を記録する。
- Auth.jsの認証を画面とAPIに適用する。
- RBACを画面とAPIに適用する。

### 完了条件

- CSVで主要データを出力できる。
- CSV import前に検証結果と差分を確認できる。
- 重要操作が監査ログとして記録される。
- 権限に応じて利用可能な画面と操作が制御される。

## Phase 6: AI評価機能

### 目的

MVPのAI評価機能を、本番運用しやすい形へ再設計します。

### 主なタスク

- OpenAI互換APIをサーバー側サービスとして隔離する。
- APIキーをクライアントへ露出させない。
- メンバー一覧向けの評価コメントを再設計する。
- メンバー詳細向けの評価コメントを再設計する。
- 評価結果のキャッシュを実装する。
- 再評価の操作を実装する。
- 失敗時フォールバックを実装する。
- 利用ログを記録する。
- 必要に応じて非同期ジョブ化を検討する。

### 完了条件

- AI評価を安全にサーバー側から実行できる。
- 評価結果を再利用でき、不要なAPI呼び出しを抑制できる。
- AI API障害時にも画面全体が壊れない。
- 利用状況を追跡できる。

## Phase 7: 本番化・運用準備

### 目的

本番リリースに向けて、テスト、デプロイ、運用手順、監視を整備します。

### 主なタスク

- Playwrightで主要E2Eを整備する。
- GitLab Container Registryへのpushを整備する。
- 環境別deployを整備する。
- production deployにはmanual approvalを挟む。
- migration checkを整備する。
- 本番DB migration手順を整理する。
- rollback方針を整理する。
- セキュリティ、監査、バックアップ、運用監視、障害対応手順をドキュメント化する。

### 完了条件

- 主要業務フローがE2Eで検証される。
- dev、staging、productionのデプロイ方針が決まっている。
- 本番反映とDB migrationの手順が明文化されている。
- 運用開始後の監視、バックアップ、障害対応の基本方針がある。

## 受け入れ条件

- `ROADMAP.md` 単体で、開発順序と各フェーズの成果物が分かる。
- `docs/TECH_STACK.md` と技術方針が矛盾しない。
- モジュラーモノリス型を採用する理由、注意点、モジュール境界が明記されている。
- GitLab CI/CD、PostgreSQL、Prisma、Auth.js、Docker、Kubernetesの位置づけが明確。
- MVPからの改善ポイントがロードマップ上のフェーズに対応している。
