## 進め方の振り返り

- 監査ログと CSV の画面は、プロトタイプ（`AuditLogs.dc.html`、`CsvExport.dc.html`、`CsvImport.dc.html`）で合意してから実装した。
- GitLab.com のクレジットが減ったため、CI を日報アプリと共用の社内ランナーへ移した。社内ランナーは遅く通信も不安定なため、ジョブを減らし、e2e は Claude が MR の前に手元で全件流して結果を MR に書く運用にした。
- 社内ランナーが止まっていた間は、前のタスクのブランチの上に次のタスクを積んで進め、ランナーが戻ってから順に merge した。
- 画面の確認は、撮影（ui:check）で行を開いた状態や確認の段階まで撮るようにし、プロトタイプとのずれを merge 前に直した。

## 発生した問題と対応

| 問題                                                                     | 原因                                                                                              | 対応                                                                                                                                                                                                            |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 監査ログの記録で業務の操作ごと失敗するおそれ                             | 差分の項目名（`changedFields`）を DB の列として渡していた。単体テストは模擬 DB のため検出できない | metadata に入れる形に直し、E2E で実際の DB への記録を確認した（!51）                                                                                                                                            |
| 監査ログの一覧が件数とともに重くなる作り                                 | 期間内の全件を読みアプリ側で絞り込んでいた                                                        | 絞り込み・件数・ページ分けを DB で行う（!53）。往復を並行にまとめた（!59）                                                                                                                                      |
| メンバーの CSV 取り込みが数十人で時間切れになるおそれ                    | 初期パスワードのハッシュ（bcrypt）を1人ずつトランザクション内で作っていた                         | 取り込みごとに1回だけ作り、トランザクションの上限を60秒にした（!56）                                                                                                                                            |
| スキルの編集ダイアログで、保存直後に開き直すとレベルの目安が空に見える   | 一覧の再取得が届く前の古いデータを表示していた                                                    | 最新の一覧から引き、再取得が届いたらフォームを作り直す（!54）                                                                                                                                                   |
| 期間の指定で「問題が発生しました」                                       | 日付の入力途中の値でサーバーが例外を投げていた                                                    | 正しい期間のときだけ絞り込み、サーバーも不正な値は初期値にする（!59）                                                                                                                                           |
| 社内ランナーでの CI の失敗                                               | 外部への通信の不安定さ、Docker Hub の取得回数の上限、ランナーの停止                               | 失敗したジョブの再実行、デモ DB の作業は共有ランナー、変数 `RUNNER_TAG` で検証も共有ランナーに切り替えられるようにした（!58）。ランナーの設定（`pull_policy`、Docker Hub へのログイン）は利用者が管理者に相談中 |
| Codex の作業がタイムアウトで途中終了、古いジョブの記録が残り再開できない | Codex のサブエージェントの制限時間と、停止したジョブの記録                                        | 新しいタスクとして、今の差分を引き継いで残りを依頼した                                                                                                                                                          |

## 残課題

- 社内ランナーの安定性（`pull_policy: if-not-present` か Docker Hub へのログイン）。利用者がランナーの管理者に相談中。
