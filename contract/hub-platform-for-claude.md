# Hub 基盤の決まり（Claude Code 向け）

Hub シリーズの製品（TalentHub など）のリポジトリで作業する Claude Code に、基盤（共通のログイン・テナント・社員情報・クラスタ）の決まりを伝えるファイル。Hub のリポジトリの `CLAUDE.md` から読み込む。

契約の版: `hub-contract/v0.20.0`。Hub の側で書き換えない。基盤の版を上げたときに、丸ごと置き換える。

## 読む資料

このファイルは、禁止と義務の要約。表・数値・手順は `contract/guide.md`（利用ガイド。下の「§N」はその節）にある。次の作業の前には、表の資料を読んでから手を付ける。推測で書かない。スキルは `.claude/skills/` にある作業の手順。

- `contract/` の中は基盤から取った写し。書き換えない。版を上げるときは `scripts/update-contract.sh <版>` で丸ごと置き換える。`contract/hubs/<製品名>/` は、ほかの Hub の定義を `scripts/hub-contracts.sh <製品名> --take` で取り込んだもの。これも手で書き換えない。
- `.claude/skills/hub-*/`（基盤が配るスキル）と、`scripts/` の基盤のスクリプト 3 本（`update-contract.sh`、`hub-contracts.sh`、`devkit.sh`）も、同じコマンドで置き換わるので、書き換えない。Hub 独自のスキルは `hub-` で始まらない名前で足す。
- 写しが無いリポジトリでは、`scripts/update-contract.sh` で取り直す。取れないときは、基盤のリポジトリ（`chosen-ryoiki-group/hamburg/hub-platform`）の `guide/README.md`、`deploy/helm/hub-app/README.md`、`design/` が同じ内容。

## してはいけないこと

- ログイン画面、ログイン API、セッション、独自の Cookie を作らない。ログインは基盤のものを使う。
- `X-Auth-*` 以外のヘッダ（`X-User-Id`、`Authorization` など）で利用者やテナントを判断しない。クライアントが自由に付けられる。
- マニフェストに、`Ingress`・`NetworkPolicy`・`Namespace` など、§2 の表にある種類のリソースを書かない。配布が失敗する。経路・外向きの宛先・資源の上限は、基盤のリポジトリの一覧ファイルに書く。
- 基盤の DB、Redis、NATS、内部用の gRPC ポート（§4.1）につながない。届かない。
- ユーザー・組織のテーブルを自分の DB に複製しない。必要なときに gRPC で引く。
- ほかの Hub の DB を読まない。ほかの Hub が「ほかの Hub 向け」として出していない API を呼ばない。
- ブラウザから、ほかの Hub の API を呼ばない。ブラウザを中継にして、ほかの Hub の情報を自分のサーバへ運ばない。自分のサーバが gRPC で取り、自分の画面に渡す。
- ほかの Hub の口や基盤の機能がまだ無いときに、回り道（ブラウザで中継する、外部のサービスを直接呼ぶ、相手の内部の API や内部用のポートを呼ぶ）を作り込まない。Hub の中で代わりを作らず、人に伝える。
- gRPC の `x-tenant-id` に、利用者の入力・URL・リクエストの本文から取った値を入れない。入れるのは、入口で受け取った `X-Auth-Tenant-Id` か、それを自分の DB に保存した値（入口のヘッダが無い定期実行で使う。§4.4）だけ。
- CSRF の検査と、製品が有効かどうかの判定を、サーバに実装しない。入口が行う。
- 通知のリンク先（`link_path`）に、自分の接頭辞の外のパスや URL を入れない。受け付けられない。
- 利用者が画面で待つ処理から、社内のモデルを直接呼ばない。1 回に数分かかり、断られることもある（社外のモデルは呼んでよい。§4.9）。
- 日報の本文と、日報から作ったデータを、社外のモデルに渡さない。`allow_external` を立てるのは、社外に渡してよいデータの呼び出しだけ。外部の LLM を Hub から直接呼ばない。
- LLM に渡す指示・本文・結果を、Hub のログに出さない。利用者の個人情報は、生成に必要な分だけを入れる。モデルの名前をコードに固定しない。空で渡すか、`ListModels` で取る。
- 画面の色・寸法を、自分で決めた値で書かない。`contract/design/tokens.css` の変数を使う。例外は主の色の上書き（`contract/design/README.md`「主の色」）だけ。
- デスクトップ版の殻・窓・通知の重なりを防ぐ仕組みと、殻の中だけに効かせる CSS・判定（窓のボタンのために空ける余白など）を、Hub の側に作らない。殻だけにある機能を前提にしない（ブラウザで開いても同じように動かす）。

## 必ずすること

- 利用者の身元は、リクエストごとに `X-Auth-*` ヘッダから取る。`X-Auth-Request-Id` をログに出す。
- 自分の DB へのアクセスは、必ず `X-Auth-Tenant-Id` で絞る。アプリの書き忘れがあっても他のテナントの行が見えないことを、DB の層で保証する（方式は自由）。
- パスは自分の接頭辞の下だけに作る（TalentHub なら画面は `/talent`、API は `/api/talent/v1`）。
- 基盤の gRPC の接続先は環境変数で受け取る。呼び出しには時間制限を置く。基盤が応答しなくても、基盤に依らない機能は動かし続ける。
- 画面から POST / PUT / PATCH / DELETE を送るときは、Cookie `csrf_token` の値を `X-CSRF-Token` ヘッダに入れる（画面の経路への Server Actions などは、`Origin` が同じなら無くてよい。利用ガイド §3.4）。
- 通知と LLM の呼び出しでは、要求の項目 `product` に自分の製品名（環境変数 `HUB_NAME`）を入れる。
- 通知の宛先は、入口で受け取ったテナントの利用者だけにする。応答の `rejected_user_ids`（送られなかった宛先）を確かめる。同じ通知の送り直しには、同じ `idempotency_key` を渡す（依頼ごとに決まる値。例: `<出来事の種類>:<対象の ID>`）。
- 社内のモデルは、定期実行やジョブから呼び、結果を自分の DB に置く。社内・社外のどちらのモデルでも、結果が無くても機能が動くように、LLM を使わない代わりを持つ。定期実行は、製品が無効になったテナント（`PermissionDenied`）を飛ばして続ける。

## 入口で届くヘッダ

認証つきの経路で届くのは `X-Auth-Tenant-Id` `X-Auth-Tenant-Slug` `X-Auth-User-Id` `X-Auth-User-Role` `X-Auth-Request-Id`（中身は §3.2）。

- クライアントが同じ名前で送っても、入口が上書きする。JWT、セッション ID、Cookie は届かない。 `X-Auth-User-Role` は基盤でのロール。Hub の中の権限は Hub が自分で持つ。
- 未ログイン・製品が有効でない・CSRF の不一致は、Hub に届く前に入口が 401 / 403 を返す（§3.3）。画面の経路を未ログインで開くと、入口がログインの画面へ移す。画面は、API から 401 を受けたらブラウザを `/login?callbackUrl=<今のパス>` に移す（§3.7）。ログインの画面は基盤が持つ。
- 認証なしの経路（一覧ファイルで `public: true`）には、身元のヘッダが届かない。テナントのデータを返さない。

## 基盤の gRPC

- 平文の gRPC。Hub の namespace から届くのは、Hub 向けの 4 つの口（社員情報と組織、テナント、通知、LLM）だけ。接続先は環境変数 `PLATFORM_USER_ORG_GRPC_ADDR` / `PLATFORM_TENANT_GRPC_ADDR` / `PLATFORM_NOTIFICATION_GRPC_ADDR` / `PLATFORM_LLM_GRPC_ADDR` で入る（§4.1）。製品名と環境は `HUB_NAME` / `HUB_ENV`。コードに接続先を直接書かない。
- 呼べるのは §4.3 の表のメソッドだけ。proto に載っていても、ほかは `PermissionDenied` になる。
- メタデータ `x-tenant-id` を必ず付け、`x-request-id` に `X-Auth-Request-Id` の値を入れる（§4.4）。
- エラーは、§4.7（通知は §4.8、LLM は §4.9）の表のとおりに、再試行するもの・しないもの・実装の誤りを分ける。
- 一覧画面などで何人分も引くときは、`GetUsers` や `GetNodeMembersBatch` でまとめて引く。
- 通知と LLM には上限がある（長さ、件数、回数、断られる時間帯、1 回の時間。§4.8 / §4.9）。コードを書く前に読む。社内のモデルを呼ぶ側の時間制限は、§4.9 のとおり長くする。社外のモデルは、基盤が許可した Hub の一覧（`ListModels`）にだけ出る（今は、本物の環境では出ない）。新しい製品が通知を使うには、基盤の側に接頭辞の登録が要る（人に伝える）。
- ブラウザからは、基盤の REST（`/api/v1/...`）をそのまま呼ぶ。Hub のサーバを経由させない。使ってよい API と呼び方は §5。

## 画面を作るとき

- `contract/design/tokens.css`（CSS の変数）を読み込み、色・文字・余白・角・影・枠の寸法を変数で書く。ヘッダと左のナビは `layout.md`、ボタンや表などは `components.md` のとおりに作る。組んだ実物は `example.html`。 共通なのは見た目の決まりだけ。ヘッダとナビに何を置くかは、この Hub が決める（左に製品の名前、右端に本人のメニュー、は共通）。共通の部品は無いので、自分の枠組みで作る。
- ヘッダの高さは変えない。ヘッダの要素には class `hub-header` を付ける（デスクトップ版の殻が、これを目印に窓のボタンの分を空ける。`layout.md` の §6）。
- ダークモードは作らない。注意を引くための点滅は使わない。文言はビジネスニュートラルにする（`contract/design/README.md`）。

## 手元で動かす

- 手元で画面や API を通して確かめるときは、hub-devkit（開発用の入口と、偽の基盤）を使う。起動・ログイン・止め方は、スキル `hub-local-check`。
- `.devkit/` は基盤から取り込んだもの。書き換えない。git に入れない。版を上げるときは `scripts/update-contract.sh <版>`。この Hub の持ち物は `docker-compose.yml` と `dev/devkit.yaml`。
- devkit は手元の代わり。本物と違う点（`.devkit/README.md` の「本物との違い」）に頼るコードを書かない。devkit のためだけの分岐を、アプリのコードに入れない。

## ほかの Hub の情報が要るとき

- ほかの Hub の情報が要るとき、基盤に無いものが要るときは、作る前に `scripts/hub-contracts.sh` を流し、各 Hub が公開している口と予定の一覧を見る（基盤のリポジトリの最新を読む。写しは持たない。使い方はスキル `hub-other-hub`）。コマンドが無いリポジトリでは、基盤のリポジトリの `contract/hubs/README.md` を読む。
- 一覧での状態（出している・予定している・無い）ごとにすることは、§12.4 の「調べる順」の表。通信を開けるための一覧ファイルの変更と、issue を出すことは、人に伝える。予定の口は、相手の口なしでも動くように作って待つ。
- コードは、`--take` で取り込んだ定義から作る。サーバ同士は gRPC でつなぎ、メタデータ `x-tenant-id` には、基盤を呼ぶときと同じ値（§4.4）を渡す。
- 自分の Hub が、ほかの Hub 向けに口を出すときは、説明と定義を自分のリポジトリの `contract-out/`（`README.md`、`hub.yaml`、`proto/`）に置く。予定だけのときも置く。書式は `contract/hubs/FORMAT.md`。

## クラスタに載せる

- Hub のリポジトリに置くのは設定ファイル（`deploy/` の `values.yaml` / `values-dev.yaml` / `values-prod.yaml`）だけ。Deployment や Service の YAML は書かない。サービス・環境変数・レプリカ数・定期実行を変えるときは、設定ファイルを直す。
- `kubectl` や `helm` を直接は使わない。新しい版は、CI が `values-<環境>.yaml` の `tag` を書き換えて出す（dev は `main` へのマージで自動、prod は人が sync する。§6.1）。イメージの作成とタグの書き換えは、基盤の CI のひな形（`.hub_build_image` / `.hub_update_tag`）を使う。サービスを足したら、`TAG_KEYS` にも足す。CI のジョブには `tags: [on-premises-runner]` を付ける（付けないとジョブが始まらない）。
- DB が要るサービスには、設定ファイルで `db: true` と書く。DB・ロール・パスワードを自分で作らない。接続情報は環境変数（`DATABASE_URL`、または `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASSWORD`）から読む。テーブルは設定ファイルの `migrate`（`db: <サービス名>` を書く）で作る。サービスに入るロールはテーブルを作れない。`DATABASE_URL` の `sslmode` の扱いは §6.1。
- DB はサービスごとに 1 つ。ほかのサービスの DB を読む設計にしない。サービス同士は API でつなぐ。
- 設定ファイルに `imagePullSecret` やレジストリの認証情報を書かない。基盤が namespace に入れてある。
- 秘密の値（パスワード、トークン）を平文で設定ファイルに書かない。`kubeseal` で暗号化した文字列を `sealedSecrets` に書く。暗号化は人に頼む（平文を扱うため）。
- 経路（URL のパス）・外向きの宛先・資源の上限は、基盤のリポジトリの `deploy/applications/hubs/<名前>-<環境>.yaml` に書く（変更は基盤のリポジトリへの MR。人に伝える）。新しい経路は、設定ファイルやコードだけでは届かない。一覧ファイルの `routes` にも足す。外への通信は既定で閉じているので、Hub 専用の DB や外部の API を使うときは `extraEgress` に宛先を足す。
- namespace は `<名前>-<環境>`。資源の既定値と上限は §6.2 / §6.3。

## まだ無いもの

基盤がまだ出していないもの（イベントの購読、Hub 同士の通信を開ける仕組み、ほかの Hub 向けの gRPC のポート、安定を約束した REST の一覧、共通の画面の部品と製品の切り替え）と、それまでの扱いは §8。必要になったら、作り込む前に基盤の担当に相談する。
