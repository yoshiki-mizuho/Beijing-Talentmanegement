# 既存のアプリを Hub に載せ替えるときの点検表

`SKILL.md` の 1〜4 で使う、詳しい観点とつまずきやすい点。最初の例は TalentHub（Next.js 16、Prisma、PostgreSQL。自前のログインと DB を持って動いていたもの）の載せ替え。ほかの言語・フレームワークでも、観点は同じ。

このスキルは、TalentHub の載せ替えで使いながら直している試しの版。載せ替えが終わったら、基盤の担当と中身を見直し、基盤のリポジトリの `contract/skills/hub-migrate-app/` に移すかを決める。移すときは、フォルダ名と `name` を `hub-migrate-app` に戻す（`hub-` で始まるスキルは、`scripts/update-contract.sh` が基盤の写しで置き換えるので、それまでは `hub-` で始まらない名前で置いている）。

## 1. 差を洗い出すときの観点

| 観点 | 今の作りで見るところ | 決まり | つまずきやすい点 |
|---|---|---|---|
| 身元 | ログイン画面、セッション、Cookie、パスワードの表、パスワードの変更・初期化、ログイン回数の制限 | 基盤が持つ。Hub は `X-Auth-*` だけを信じる（§2、§3） | パスワードに関わる画面・メール・監査の記録・テストがまとめて不要になる。権限（管理者・マネージャーなど）は Hub の表に、基盤の利用者 ID をキーにして持ち直す |
| 書き込みの CSRF | 画面からの書き込みの送り方 | 入口が `X-CSRF-Token` を検査する。Hub は検査しない（§3.4） | フレームワークが内部で送る POST（Next.js の Server Actions、素のフォームの送信など）は、独自のヘッダを付けられないことがある。付けられなければ、書き込みを API に作り替える大きな作業になる。最初に基盤に聞く |
| テナント | テーブルの作り、問い合わせの書き方 | 全テーブルに `tenant_id`。DB の層で、ほかのテナントの行が見えないことを保証する（§2、§6.1） | ORM の接続の使い回しと相性が悪い。リクエストごとにトランザクションの中で `set_config('app.tenant_id', …, true)` を流してから読み書きする、などの形を決める。定期実行で全テナントをまたぐ処理は、§6.1 の `SECURITY DEFINER` の関数で対象だけを引く |
| 社員・組織 | 社員・部署・上司・役職の表、それを登録する画面と CSV、氏名での検索・並べ替え | 写しを持たない。gRPC で引く。Hub 固有の属性は `user_id` と `tenant_id` で持つ（§4.3、§4.6） | 一覧の氏名・部署は `GetUsers` などでまとめて引き、短い時間だけ覚える。氏名での検索や並べ替えは、テナントの利用者をまとめて引いてからアプリの中で行う。上司・担当範囲は §4.3 の上長・リーダーの関係から取る。社員番号やメールで行を結び付けていた取り込みは、利用者 ID への結び付け方を決め直す |
| LLM | ボタンを押して待つ AI の機能、外部の AI の窓口 | 社内のモデルは画面で待たせない。1 回 1〜5 分、1 日 50 回まで。外部の AI を直接呼ばない（§4.9） | 依頼を表に記録し、定期実行が作って結果を置く。画面は「作成中」を出し、開き直すと結果が出る形にする。上限・断られる時間帯・失敗のときに、LLM を使わない代わり（決まった組み立ての文など）を出す。指示・本文・結果をログに出さない |
| 通知 | アプリの中の通知 | 基盤の通知も使える。リンク先は自分の接頭辞の下だけ（§4.8） | アプリの中の通知を残すか、基盤の通知に寄せるかを決める。使うときは接頭辞の登録を基盤に頼む |
| パス | アプリの URL の根、API の場所 | 画面は `/<接頭辞>`、API は `/api/<接頭辞>/v1` の下だけ（§2） | フレームワークの「根のパス」の設定（Next.js の `basePath` など）は API にもかかる。API を `/api/<接頭辞>/v1` で受けるには、転送の設定か、経路の分け方を決める |
| 見た目 | 色、寸法、ヘッダとナビ、演出、文言 | `tokens.css` の変数、`layout.md` の枠。主の色だけ変えてよい。動きは読み込み中だけ、文言はビジネスニュートラル（§15） | 紙吹雪・ポップの動き・あおる文言など、利用者が気に入っている演出がぶつかる。控えめにするか、基盤に相談するかを利用者と決める |
| 配布 | 今の公開先（PaaS など）、ビルド、マイグレーション | イメージと `deploy/` の設定ファイル。DB は `db: true`、テーブルは `migrate` のジョブ、定期実行は `cronJobs`（§6.1） | マイグレーションの道具をそのまま `migrate` のジョブのイメージで動かす。サービスに入るロールはテーブルを作れない。今の公開先は、載せ替えの前の版で止めて残すか、片付けるかを決める |
| 手元の確認とテスト | ログインして操作する E2E、手元の起動 | hub-devkit は Docker が要る（§9.1）。無ければ、アプリを直接ヘッダ付きで呼ぶ（§9.2） | パスワードでログインする E2E は全部作り直しになる。手元では、ヘッダを付けて中継する小さな仕組みを、アプリの外に置く（アプリの中に開発用の分岐を入れない） |

## 2. 利用者に聞くことの例

- 演出と文言を、見た目の決まりにどこまで合わせるか（控えめにする／基盤に例外を相談する／今のまま）。
- LLM の機能を、裏で作ってできたら表示する形にするか、当面は LLM を使わない形だけにするか。
- 上司・部下と担当範囲を、基盤の組織から取るか、Hub の中で設定し続けるか。
- 今の公開環境（デモなど）を、載せ替えの前の版で止めて残すか、片付けるか。
- 今のデータを引っ越すか（まだ運用データが無ければ、新しく始めるのが楽）。

## 3. 基盤に聞くことの例（§6.4 の「基盤への質問」）

- フレームワークの組み込みの送信と、入口の CSRF の検査の関係。
- 画面と API を 1 つのサービスで受けてよいか（一覧ファイルの `routes` で同じサービスを指す）。
- 手元で Docker が使えないときの確かめ方、CI で devkit を使うこと。
- 製品名と接頭辞、通知の接頭辞の登録。

## 4. 進め方の注意

- 段の順番は、身元 → テナント分離 → 社員・組織、が互いに深く関わる。1 段ずつ終えて、既存のテストを通してから次へ進む。
- テナント分離の段では、「テナント A の利用者で、テナント B の行が読めない・書けない」ことを、DB の層だけを使うテストで確かめる。
- 社員・組織の段では、基盤が応答しないときに、基盤に依らない機能が動き続けることを確かめる（gRPC に時間制限を置く）。
- 載せ替えの途中で、利用者の手元のデモや公開環境が動かなくなる時点を、先に伝えておく。
