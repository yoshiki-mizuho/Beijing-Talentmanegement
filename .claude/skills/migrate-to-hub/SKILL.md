# 既存のアプリを Hub に載せ替える

新しく作る Hub は hub-template から始める。これは、自前のログインや DB を持って動いているアプリを、基盤に合わせて作り替えるときの手順。詳しい点検の観点と、つまずきやすい点は、同じフォルダの `checklist.md`。

## 1. 差を洗い出す（コードを変える前）

`contract/guide.md` を読み、アプリの今の作りと、次の観点ごとに見比べて、表にまとめる。推測で埋めず、コードとガイドの両方を確かめる。

- 身元：自前のログイン・セッション・Cookie・パスワードを外し、`X-Auth-*` で受け取る。Hub の中の権限は利用者 ID に結び付ける（§2、§3）
- 書き込み：入口が `X-CSRF-Token` を検査する。フレームワークの組み込みの送信（フォームの POST、サーバーの関数を呼ぶ仕組み）がヘッダを付けられるかを確かめる（§3.4）
- テナント：全テーブルに `tenant_id` と DB の層での制限を入れる（§2、§6.1）
- 社員・組織：氏名・メール・部署・上司の表を持っていれば消し、gRPC で引く。その登録画面や取り込みも役目を失う（§4.3、§4.6）
- LLM：画面で待たせている呼び出しは、定期実行かジョブに移す。1 日の上限と、LLM を使わない代わりを持つ（§4.9）
- パス：画面と API を自分の接頭辞の下に移す（§2）
- 見た目：色と寸法は `tokens.css`。動きと文言の決まりと、今の演出を見比べる（§15）
- 配布と手元の確認：イメージ、`deploy/` の設定ファイル、マイグレーションのジョブ、定期実行。手元で Docker が使えなければ §9.2 の形（§6.1、§9）

## 2. 決めることを人に聞く

差のうち、作り替え方が 1 つに決まらないものは、選択肢と推奨を添えて利用者に聞く。よく出るのは、演出と文言をどこまで控えるか、LLM の機能を裏で作るか止めるか、上司・担当範囲を基盤の組織から取るか、今動いている公開環境をどうするか、データを引っ越すか。

## 3. 基盤に聞くことを先に出す

ガイドに答えが無く、作り替えの大きさが変わるもの（組み込みの送信と CSRF、経路の分け方、CI で devkit を使うこと、製品名と接頭辞、通知の登録）は、作り始める前に、人に基盤のリポジトリの issue で聞いてもらう（§6.4）。文案は作ってよいが、出すのは人。

## 4. 順番に作り替える

1. 土台：契約の写しとスクリプトを取り込む（`scripts/update-contract.sh`）。経路、イメージ、`deploy/`、CI
2. 身元と書き込み → 3. テナント分離 → 4. 社員・組織 → 5. LLM → 6. 見た目 → 7. 載せる（§6.2、§6.4）

各段の終わりに、既存のテストを通し、テナントをまたいで見えないことのテストを足す。1 段を 1 つ以上の MR に分け、段をまたいで混ぜない。
