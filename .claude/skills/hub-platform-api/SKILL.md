# 基盤の口を使う

## 読む資料

- `contract/hub-platform-for-claude.md` の「してはいけないこと」「必ずすること」「基盤の gRPC」
- `contract/guide.md` §4（接続先 §4.1、呼べるメソッド §4.3、メタデータ §4.4、社員情報の持ち方 §4.6、エラー §4.7）、通知は §4.8、LLM は §4.9、ブラウザからの REST は §5
- `contract/proto/` の、使うサービスの proto（項目の意味はコメントにある）

## 手順

1. 口を選ぶ。
   - 画面が本人の情報を出す・ログアウトする → ブラウザから基盤の REST（§5）。Hub のサーバを経由させない
   - サーバが利用者・組織・テナントの情報を使う → §4.3 のメソッド。何人分も引くときは、まとめて引くメソッドを選ぶ
   - 利用者に知らせる → 通知（§4.8）
   - 文章・JSON を作る → LLM（§4.9）。社内のモデルは、利用者が待つ処理からは呼ばず、定期実行やジョブから呼んで結果を自分の DB に置く。社外のモデルを使ってよい場面と条件は §4.9 の表の「社外のモデル」
   - どれにも無い → `contract/guide.md` §8 を見て、作り込まずに人に伝える
2. 使う proto を読み、`CLAUDE.md` の「この Hub の決まり」にある、定義からコードを作るコマンドでクライアントを作る。`contract/proto/` は書き換えない。
3. 接続先は環境変数から取る（§4.1）。呼び出しに時間制限を置く。メタデータは §4.4 のとおりに入れる（入口のヘッダ §3.2 の値。定期実行のときの扱いも §4.4）。
4. エラーを §4.7 の表のとおりに分ける。基盤が応答しないときも、基盤に依らない機能は動かす。
5. 通知・LLM は、上限と断られる場面（§4.8 / §4.9）を読み、要求の項目を決まりどおりに入れる。
6. スキル `hub-local-check` で通して確かめる。偽の基盤の動きは `.devkit/README.md` の「偽の基盤（gRPC）がすること」。

## 確かめること

- 呼んでいるメソッドが、全部 §4.3 の表にある
- テナントの ID を、利用者の入力・URL・本文から取っていない（§4.4）
- 接続先・モデルの名前をコードに固定していない。時間制限がある
- 社外のモデルを使うとき: `ListModels` の `model_infos` に出ているものだけを選び、`allow_external` を立てている。渡すデータが日報に由来しない。止まったときの、LLM を使わない代わりの処理がある
- 手元で、成功の場合と、基盤がエラーを返す場合（通知・LLM は `/_devkit` で起こす）の両方を見た
